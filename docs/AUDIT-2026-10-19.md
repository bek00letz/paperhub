# Audit, 19 October 2026

A first read of Paperhub (`main` at `491263f`, version 1.5.4), with one
question in mind: e-paper panel has moved a long way since Paperhub was copied
from it, so which of those changes would make Paperhub better?

**How it was checked.** I read the add-on (server, renderer, feeds, kiosk, the
Linux client, docs), ran the suite (42 tests pass), and compared it file by
file with e-paper panel's history. Findings marked *confirmed* were reproduced
with a throwaway render outside the repository. Nothing was changed in either
repository or in Home Assistant.

## Where Paperhub came from

Paperhub was copied from e-paper panel on the morning of 17 October, around
e-paper **0.8.8**. `render/binding.py` and `feeds/` are still identical to
e-paper's code from then. Everything else (theme, layout, server) was
rewritten for grayscale, touch and many devices. Paperhub then went from 1.0
to 1.5.4 in one day.

e-paper has made 100 commits since (0.8.9 → 0.10.1). Most of them fix
problems that Paperhub inherited, or that Paperhub's rewrite brought back in a
new form.

## The concept

The idea is sound, and it is different enough from e-paper panel to be its
own product:

| | e-paper panel | Paperhub |
|---|---|---|
| Screen | one 5.79″ 1-bit panel, 3 m from the sofa | many e-readers, 300 ppi, at arm's length |
| Input | five buttons on the panel | touch, which is the main way in |
| What fits on a screen | one fact | a real dashboard: tiles, grids, a calendar |
| Client | ESPHome firmware written for the project | a browser, a jailbroken Kindle, TRMNL |

One thing e-paper has that Paperhub lacks is a single, measured constraint
that every design decision follows from (e-paper's is "one readable line costs
40 % of the screen"). For Paperhub it is probably this: **every e-ink repaint
costs a few hundred milliseconds and a visible flash, so a tap should cause
exactly one repaint, and that repaint should already show the result.**
Several findings below break that rule.

## Part 1: Problems found

Most severe first. "e-paper" says whether e-paper panel has already solved it.

### 1. Home Assistant's token can end up in the add-on's log — High

When a call fails, the error is printed with `{exc!r}`. aiohttp's errors
include the request headers when printed like that, so the line can contain
`Authorization: Bearer <the add-on's token>`. This happened for real in
e-paper: the token was in its log after a Home Assistant restart.

- `server.py:252` (every action a tap triggers), `:382`, `:469`, `:589`, `:748`, `feeds/__init__.py:102`
- Error text is also sent back to the browser (`str(exc)`) in several editor endpoints.

**e-paper:** solved in 0.10.1. `health.describe(exc)` is the only way an error
reaches a log or a response, and a test fails if a fake token shows up in the
output.

### 2. The editor answers every add-on, not only Home Assistant — Medium-high

Port 8080 isn't published to the LAN, but every other add-on on the
Supervisor's internal network can reach it, with no login. Through it,
anything can rewrite the layouts, change devices, and call Home Assistant
actions (the touch simulator calls whatever service a page names).

**e-paper:** solved in 0.9.2. An `ingress_only` middleware refuses anyone who
isn't Home Assistant's Ingress proxy (`172.30.32.2`).

### 3. On the LAN, anyone on the Wi-Fi can press buttons — Medium

The frame token is optional and empty by default, so `POST /api/touch` from
any device on the network triggers whatever the page's tiles do: lights,
locks, scripts. Turning the token on doesn't help yet: **the kiosk never sends
it**, so with a token set the kiosk shows nothing and taps fail. A token with
a non-ASCII character makes `hmac.compare_digest` raise (a 500 error).

**e-paper:** solved in 0.9.7. Every install gets a generated token. Frames
switch to requiring it the first time a client uses it, so nobody's screen
goes blank, and actions always require it. Paperhub needs the same, plus the
kiosk carrying the token from its own address (`/kiosk/<device>?token=…`) into
every request.

### 4. In landscape, elements on the right aren't drawn but can still be tapped — Medium (*confirmed*)

Every drawer clamps its box against the **portrait** canvas
(`_clamp_box(..., display=display)` with no orientation), while hit-testing
clamps against the real, rotated canvas. On a Boox Go 6 in landscape
(1448 × 1072), a tile at x = 1150 is drawn as a 1-pixel sliver at x = 1071,
but tapping where it should be still toggles the light.

A second, smaller mismatch: a tile saved without a size is drawn 280 × 130 but
hit-tested as 200 × 60, so the lower half of the tile doesn't respond.

**The cause** is that geometry is worked out twice, once to draw and once to
hit-test. This is the same kind of bug as e-paper's 0.8.33–0.8.37 overlay
back-and-forth, which only ended when one function owned the geometry and the
other side read its result. **The fix** here: `render_page` records the box of
everything it actually drew (including grid cells), and hit-testing reads that
record instead of recomputing it.

### 5. A render waits on ESPN, OpenSky and Home Assistant's weather — Medium

`enrich_page_values` awaits each widget's network fetch inside the render.
A tap re-renders before it answers, so a slow or unreachable service adds up
to 6–10 seconds per widget to the time between the tap and the screen
changing. For a touch product that time is the product.

**e-paper:** solved in 0.9.5 and 0.10.1. `live_data.py` fetches in the
background, so a render only reads what's already there. `sources/` holds the
fetchers. They have the **same function names and output shapes** as
Paperhub's inline ones, so Paperhub's drawers would keep working.

### 6. A built-in home location — Low-medium (privacy)

`server.py:281` starts with fixed coordinates. They look like a real place,
not a placeholder. If Home Assistant can't be reached, the flight widget shows
aircraft over that spot. It's also in a public repository.

**e-paper:** solved. There's no built-in location or timezone; Home
Assistant's settings are the source, and without them the widget says so.

### 7. Changes from Home Assistant get lost — Medium

The WebSocket listener skips any `state_changed` event that arrives within
0.4 s of the previous one. It drops them instead of collecting them. A scene
that turns on three lights redraws for the first light only. The others
appear at the next timed refresh, which can be 15 minutes away, or 24 hours
on a touch-only device. The render also runs inside the socket's read loop, so
a slow render holds up every event behind it.

**Fix:** mark the affected devices as needing a redraw, then draw each one
once after a short pause. This is new code, but it's the same idea as
e-paper's "one render at a time".

### 8. Two renders of the same device at once — Low-medium

A tap, a WebSocket event, the timer and a Send can all render the same device
at the same time. Whichever finishes last wins, even if it started first.

**e-paper:** solved in 0.10.1 with a render lock. Paperhub needs one lock per
device.

### 9. A tap probably repaints the screen twice — likely, needs a device to confirm

After a tap the kiosk reloads the frame from the touch response. The server
also announces the new version over the event stream, and the kiosk reloads
again. Both reloads add `?v=…` to the address, so the ETag never gets a
chance to answer "not modified". On e-ink that's two repaints for one tap.
The server can already return the new PNG in the touch response; the kiosk
doesn't use that.

### 10. "Done" when nothing was done — Low

- A tap reports `ok` whether or not Home Assistant accepted the action (the result of `call_ha_service` is ignored). Nothing on the screen says the action failed.
- `/api/panel-setup` and `/api/panel-refresh` are stubs left over from e-paper. They always answer `ok`, and the editor still says "Panel connected in Home Assistant".

**e-paper's rule:** "A call that can fail must say so."

### 11. Anyone can create devices — Low

Any device ID used on the LAN creates a saved device, up to 32. After that,
every new ID quietly shares the `default` device and its current page. The
TRMNL endpoint takes the ID from request headers, including `Access-Token`,
and saves it to disk in plain text. `devices.json` is also rewritten on every
tap.

### 12. Renaming a data source erases its key — Low

Masked secrets are matched back by name, so renaming a Jellyfin source while
its key shows as `••••••••` saves an empty key.

**e-paper:** solved in 0.10.1 with stable source IDs.

### 13. Flights: OpenSky only, and an old list served as fresh — Low

OpenSky's anonymous access is heavily rate-limited. On a failure, the last
list is returned forever, so aircraft can sit on the radar for hours.

**e-paper:** Flightradar24 with OpenSky as a fallback. Lists older than five
minutes are dropped. Places can be saved by name.

### 14. The docs promise numbers nobody measured

The README and the architecture doc state "2–4 weeks" of battery, "< 50 ms"
touch-to-glass, "0.0 %" idle CPU and "Regal waveform matched" refreshes, and
present an Android companion app. The repository has a spec for that app but
no app. None of these numbers were measured. e-paper's architecture doc keeps
a "Measured numbers" table and marks modelled figures as modelled. That habit
is worth copying before anyone installs this expecting weeks of battery.

Also, `AGENTS.md` has its own paraphrase of the Apple rule instead of the rule
itself, word for word.

## Part 2: What to bring over from e-paper panel

### Ports almost as-is

| From e-paper | What it gives Paperhub | Fixes |
|---|---|---|
| The `server.py` split (`config`, `runtime`, `web`, `ha`, `layouts_store`…), done in e-paper's `4a3bfdb` with no behaviour change | A 1,857-line file becomes modules the other ports slot into | — |
| `health.py` | Safe error text everywhere, per-service status, a test that the token never reaches the log | 1, 10 |
| `web.ingress_only` | Editor only answers Home Assistant | 2 |
| `frame_token.py` | A token on every install, switched on without blanking anyone's screen | 3 |
| `live_data.py` + `sources/` (flights, sports, racing, weather, calendars, home location) | Renders never wait on the internet; failing services visible | 5, 6, 13 |
| `feeds/` and `render/binding.py` updates | Stable source IDs, time limits on statistics, Jellyfin details as their own attributes, newer binding options | 12 |
| `render/units.py` | 1,234 W reads 1.23 kW without a template | — |
| `layouts_store` checks, saves with `If-Match`, drafts | Two editor windows can't overwrite each other; one bad number can't stop all rendering | — |
| The behaviour and security tests | Pins the above so it stays fixed | — |

### The same ideas, new code

| e-paper idea | In Paperhub |
|---|---|
| One render at a time | One per device, with changes collected over a short pause (7, 8) |
| The server owns the geometry | The renderer records what it drew; taps are checked against that (4) |
| The add-on's values as Home Assistant entities over MQTT | Each device's battery, last seen and current page as sensors, plus a problem sensor per service, so an automation can say "the Kindle's battery is low" |
| Conditional and alert pages, with `linger` | Paperhub has no `show_if` or alert pages. That's a feature decision, not a fix |
| The new editor's rules (drafts, undo toasts instead of dialogs, 44 pt targets, nodes built with `h()` rather than HTML strings) | Paperhub's editor is one 4,876-line file; see the question below |

### Doesn't translate

The EPF frame format, the firmware and `PanelController`, ESPHome panel
setup, fitting pages into 2 MB, the page strip and sub-item rotation, the
physical buttons, and the "no grey" 1-bit rules. Those are about one specific
panel. e-paper's ghost-clearing policy (when to do a full refresh) may matter
later for the kiosk on Boox devices, but only once there's a device to
measure on.

## Part 3: Suggested order

1. **Split `server.py`** the way e-paper did, with no change in behaviour. The suite stays green, and every later port becomes a matter of copying modules.
2. **Safety:** `describe()`, Ingress-only, a token by default with the kiosk carrying it (1, 2, 3).
3. **Background data:** `live_data` and `sources/`, collected WebSocket redraws, a render lock per device (5, 6, 7, 8, 13).
4. **One geometry:** a hit map from the renderer (4), with a test that renders landscape and taps every element.
5. **Saving safely:** layout checks, `If-Match`, drafts, the `feeds/` updates (12).
6. **Then decide:** the editor, Home Assistant entities per device, conditional pages, honest docs (14).

**Copying, not sharing.** I'd copy e-paper's modules into Paperhub rather than
build a shared package. They will change at different speeds, and a shared
package would tie two release cycles together. Each ported file should say
which e-paper commit it came from, so a later sync is one `git diff` away.
